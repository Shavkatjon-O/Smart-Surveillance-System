<Status kind="beta" /> The connector agent is built and tested against the simulated site; it has not yet run at a real site.

A connector lets a backend reach a site's cameras without opening any port at the site. It is one container on any always-on Linux machine on the site's network, such as a mini PC or a Raspberry Pi. Every call it makes to the backend is outbound.

## Run

deploy/connector in the repository runs the connector with host networking, which multicast discovery on the site's network needs. Copy its example configuration, set SSS_CONNECTOR_BACKEND_URL to the backend's address, and start it:

```bash
cp deploy/connector/.env.example deploy/connector/.env
docker compose -f deploy/connector/docker-compose.yml up -d --build
docker compose -f deploy/connector/docker-compose.yml logs -f connector
```

The container runs read-only, without capabilities and with a 512 MB memory limit. The SSS_CONNECTOR_ settings in the [configuration reference](../reference/configuration.mdx) change its name, ports, interfaces, subnets and discovery interval.

## Pair

1. The log shows a pairing code and its QR code. While the connector waits, its pairing page at port 8780, /pairing, shows the same code, and /pairing.svg the QR code.
2. An admin or owner of the site claims it in the app: by scanning the QR code, by typing the code, or by picking the connector the app finds over mDNS on the same Wi-Fi.
3. The connector, which keeps polling, receives its credentials and starts sending heartbeats. The app then lists the cameras its discovery finds.

The connector belongs to that one site until it is removed. Camera passwords entered in the app go to the connector and stay there, encrypted; the backend never stores them.

The [connector guide](../guides/connector.mdx) describes what it does once paired, and the [connector protocol](../reference/connector-protocol.mdx) the calls behind the pairing.
